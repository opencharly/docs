## What it is

`charly` is a CLI that builds container images from a declarative list of **candies**, and applies
that same list to a VM guest, a Kubernetes cluster, a host, or an Android device. Every substrate
compiles to one shared install plan, so moving a deploy from a container to a VM is a keyword
change rather than a rewrite.

Every candy also carries an acceptance plan, baked into the built image as an
`ai.opencharly.description` OCI label. The image can therefore be tested later, on a machine that
has never seen its source repository.

## How it works

### The words

Six terms, used precisely throughout. `box` and `candybox` are distinct, and are the pair most
often used interchangeably. [Full glossary →](/concepts/00-vocabulary/)

| Term | What it is | What it is *not* |
|---|---|---|
| **candy** | one entry in a `charly.yml` — the **only** entity kind there is | not "a layer", not "a package" |
| **box** | a candy carrying `base:`/`from:` → a buildable **container image** | not the running thing |
| **candybox** | a box in its **running, isolated form** — container, VM, or check bed. **The security boundary.** | not the image, not the config |
| **check bed** | a deploy marked `disposable: true` — a candybox that exists to be destroyed | not a test file |
| **plan** | the ordered acceptance spec a candy carries, baked into the image as an OCI label | not a build script |
| **substrate** | where a deploy lands: `pod:` `vm:` `k8s:` `local:` `android:` | |

### One keyword, three roles

There is one entity keyword, `candy:`, and one filename, `charly.yml`. What you put inside the
keyword decides what the entity is:

| What it declares | What it is |
|---|---|
| `package:` / `plan:` / `service:` | a **layer** — one concern, composed into any box |
| …plus `base:` or `from:` | a **box** — a buildable container image |
| …plus a `plugin:` block | a **plugin** — a new verb, kind or command for `charly` itself |

Every capability beyond the core is that third row. Verbs, deploy kinds, probes, builders and whole
command trees are all plugin candies, which is why the core stays small while the catalog grows,
and why there is no second vocabulary to learn.

### The four stages

<CardGrid>
  <Card title="Build" icon="seti:config">
    Write a `candy:` with a `base:` and a candy list; `charly box build <box>` renders a
    multi-stage Containerfile and builds the image.
  </Card>
  <Card title="Run" icon="rocket">
    `charly shell <box>` drops you inside the running **candybox** — the isolation boundary, not
    the image.
  </Card>
  <Card title="Deploy" icon="puzzle">
    Add a substrate keyword — `pod:` `vm:` `k8s:` `local:` `android:` — and the same candy list
    installs there. Under **podman or docker**, and as **systemd quadlets** where the host supports
    them.
  </Card>
  <Card title="Evaluate" icon="approve-check">
    Each candy's `plan:` is executable: `charly check box` at build scope, `charly check live`
    against a running deployment.
  </Card>
</CardGrid>

A **check bed** — a deploy marked `disposable: true` — runs all four in one command. `charly check
run <bed>` builds the image, checks it, deploys it, waits for steady state, checks it live, then
destroys and rebuilds from scratch and checks it again, then tears everything down.

### Where a running candybox lives

**Podman and docker are both first-class**, for building and for running, and the two are chosen
independently — charly auto-detects what is installed, and either can be pinned per host. Building
with podman and running under docker is a supported combination.

On a host with podman and systemd, a `pod:` deploy is realised as **user-level systemd quadlets**:
`charly config` generates one `charly-<name>.service` per deploy, carrying its ports, volumes,
devices and security settings, so `systemctl --user` manages it like any other user service and
starts it at login. A deploy with encrypted volumes and no keyring backend is the exception — it
omits `WantedBy=default.target` and waits for an explicit `charly start`, since nothing should try
to mount an encrypted volume before there is a key for it.

Where podman and systemd are not both present, the same deploy runs directly against the engine.
You do not pick between the two — the deploy is described once and charly resolves what the host
supports. [Deploy →](/recipes/core/deploy/)

### Any harness, and no agent-only surface

There is no automation-only API: the CLI *is* the surface, so anything that can run a command drives
every stage above. `charly` additionally serves its whole command tree over **MCP** (Streamable HTTP
or stdio) for any MCP-speaking client, and container-provided servers auto-discover through
`mcp_provide:`. The project's rules are written the same way — `AGENTS.md` is the complete
harness-neutral rulebook, and a per-harness file is an adapter of it rather than a second source of
truth. [You and your agents →](/concepts/04-you-and-your-agents/)

## A real box, end to end

The box below is real, shipped, and re-proven on every acceptance run — you can read it at
[`tutorial-shell`](/reference/box/fedora/tutorial-shell/). It composes two candies: `ripgrep`, a
tool layer, and `sshd`, a service layer.

```bash
charly --repo opencharly/distro-fedora box validate                    # the schema gate — nothing runs until it passes
charly --repo opencharly/distro-fedora box build tutorial-shell        # → multi-stage Containerfile → image
charly --repo opencharly/distro-fedora shell tutorial-shell            # → you are inside the candybox
charly --repo opencharly/distro-fedora check run check-tutorial-shell  # → build, deploy, probe, fresh rebuild, tear down
```

Note what the box does *not* declare: an init system. `sshd` declares a service, so charly resolves
the init this target needs and installs it — supervisord for a container, nothing extra for a
systemd machine. You declare the service; the init follows.

Then change the mold and keep the recipe — the same candy list applies to a VM guest, a cluster, or
a host. Swap the substrate in the deploy, not the recipe.
[The full walkthrough →](/start/quickstart/)

<Aside type="tip" title="Yes, it comes with the kitchen sink">
The box above has two candies. At the other end sit the **kitchen-sink dev boxes** —
[`fedora-coder`](/recipes/coder/fedora-coder/) and its [`arch`](/recipes/coder/arch-coder/),
[`debian`](/recipes/coder/debian-coder/) and [`ubuntu`](/recipes/coder/ubuntu-coder/) siblings —
around thirty candies each: four AI coding CLIs, every language runtime, DevOps tooling, nested
rootless containers and rootless VMs, all at uid 1000 with no `--privileged`. Same format, same
commands. A fully stocked kitchen really does ship with the sink.
</Aside>
