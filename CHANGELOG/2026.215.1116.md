# 2026.215.1116 — Bootstrap: the opencharly.ai documentation site

The initial content of `opencharly/docs`: a Starlight site published at opencharly.ai by
Cloudflare Pages, wired into the superproject as the `docs/` submodule.

## Two halves, maintained differently

The site is deliberately split. The **hand-authored narrative** is only what a website needs and
a repository does not have — the home page, install, quickstart, five concept pages (candies &
boxes, candyboxing, the build/run/deploy/evaluate lifecycle, RDD & ADE, schema & versions), and
two guides (authoring a plugin, the CLI). Every concept page opens from the VISION.md tenet it
operationalizes, because those tenets are why the project looks the way it does.

Everything else is **generated** by `charly docs generate` (the `candy/plugin-docs` runtime
plugin in the superproject) and carries a `DO-NOT-EDIT` header:

- `vision.md` — VISION.md verbatim, with repo-relative links rewritten for a web reader.
- `reference/cli/` — 46 pages, one per `command:` word, each naming the plugin that serves it.
- `reference/candy/` — 295 pages, every defined candy with its packages, services and its
  `plan:` published as a runnable acceptance spec.
- `reference/box/` — 80 pages, every defined box.
- `reference/plugin/` — 86 pages, every plugin candy: its providers, its placement computed from
  `compiled_plugins:` membership, and its CUE parameter schema rendered inline.
- `reference/providers.md` — the inverted index: all 137 reserved words → the plugin serving
  each. Nothing in the repository answered "what implements `cdp:`?" before this.
- `recipes/` — 320 pages: all 294 skills, their 25 `references/*.md` detail pages, and the
  landing page indexing them by the four marketplace buckets.

That is 829 generated pages, alongside 10 hand-authored ones — 839 content files, which Astro
builds into **840 routes** (the extra is its 404 page). The reason for the split is R3 and tenet
10: a second copy of the cookbook would drift, so anything that already exists in the source is
projected, never transcribed.

## Site structure

- Starlight on Astro 7, `site: https://opencharly.ai`, sidebar autogenerated from the content
  tree so a new candy, box, plugin or skill appears with no site-side edit.
- Entity pages are namespaced by DIRECTORY (`reference/box/fedora/fedora/`) rather than by a
  dotted filename: Astro strips dots when deriving a route slug, which would serve
  `fedora.check-pod.md` at `/fedoracheck-pod/` and invites collisions.
- No submodules of its own — that is what keeps the Cloudflare Pages Git integration on the
  simple path, with the build a plain `npm ci && npm run build`.

## Cross-reference integrity

Two gates, because one turned out not to be enough.

**Harness cross-references.** The skill corpus is densely self-linked in harness syntax
(`/charly-check:check` alone appears 277 times; 3788 references across 256 distinct targets).
Every one is rewritten to a site link at generation time, and an unresolvable reference fails
generation rather than emitting a dead link. The corpus is clean today, so the gate starts green.

**Every internal site link.** The gate above covers only `/charly-<plugin>:<skill>` references
inside skill bodies — which is narrower than "the docs build checks its links", and the gap was
real: the home page, the quickstart, and the generated vision page (whose rewrite table maps the
repo's `plugins/README.md` onto `/recipes/`) all linked to a path that emitted no page, because
the sidebar entry for it is an autogenerated group label rather than a route. Three dead links on
a green build. So a second gate resolves **every** site-absolute markdown link — generated and
hand-authored alike — against the pages the tree actually emits, and `recipes/index.md` is now a
real generated landing page. Regression-guarded by `links_site_test.go`.

Three guards keep real content from being mangled into links, each one earned from a real corpus
case: the skill part must start with a letter (else `redis://charly-redis:6379` matches), the
reference must not follow a `/` (URL authorities), and it must not follow a word character
(container image tags such as `localhost/charly-selkies-kde:latest`).
