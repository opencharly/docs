# 2026.231.0149 — the ollama pages say what the candy declares, not what the image contains

Docs projection of the candy prose corrections in `charly#309`, the sibling of the
`plugins` projection in `plugins#210`.

Both ollama pages asserted that GPU support is composed outside the candy — one as
"never by this candy", the other as "GPU support is composed outside it" — on pages
that ALSO state a tarball distro receives one upstream archive already containing the
CUDA backend. A reader taking the first claim plainly and then reading the second had
no way to reconcile them, and the reading it invites (a plain tarball ollama image is
CPU-only) is false.

The corrected wording separates what the candy DECLARES (no GPU dependency — true on
every distro, and the reason the backend candies exist) from what an image CONTAINS
(packaged distros are genuinely CPU-only until a backend is composed; tarball distros
carry CUDA in the archive regardless).

The `ollama` page additionally stops pointing at a size "table" it does not have —
the figures are bullets — and states the backend rule that actually holds: both
backend candies package only on Arch, and off Arch they diverge, with `ollama-cuda`
degrading into an assertion that the tarball's bundled CUDA is present while
`ollama-rocm` has no tarball path at all.

An earlier revision of this branch went further and named which boxes compose which
backend. That was FALSE and this PR's validator caught it: at the gitlinks the source
branch pins — those repositories' `main` — neither distro submodule composes either
backend candy, and the composition exists only on the unmerged `feat/ollama-plugin`
branches of `distro-fedora#18` and `distro-cachyos#15`. The enumeration is deleted at
the candy source rather than corrected, because naming boxes on this page was itself
the defect: that list lives in the distro submodules, moves there, and any copy here
goes stale the moment one of those PRs lands.

Generated by `charly docs generate` (`task docs:sync`) from the corrected candy
sources; never hand-edited.

Two further corrections to the `ollama` page, both from validator cold readers.

The paragraph's own partition was false. It opened "Every size below is INSTALLED. The one figure
above is a COMPRESSED DOWNLOAD" while THREE figures sat above it and two of those were installed
sizes — and the size-accounting fix below made that load-bearing rather than merely untidy, by
reaching above the paragraph to pull the 66 MiB base into an installed total the preamble had just
declared a download. "The one figure above" was also a COUNT, and wrong as a count, so naming a
different figure would not have fixed it. The axis no longer splits by POSITION on the page at
all; it splits by WHICH figure, with the exception named: exactly one number here is a compressed
download, and the parenthetical says why the positional framing failed so a later edit reaching
across the paragraph cannot silently re-break it.

The page also pointed at a page that does not exist — "`ollama-rocm` … says so on its own page".
Neither backend candy declares a `skill:` entity, so neither projects a page. The constraint is
stated where the reader already is, with the reason it cannot be stated anywhere else.

The size accounting on the `ollama` page is corrected in the same round, from
`plugins#210`'s cold reader: the two figures below the download line are the two
ALTERNATIVE backends, not the cost of a packaged build. A packaged image pays the 66 MiB
base plus at most one of them, and neither if it composes neither; and `~988 MiB` was
unscoped one paragraph before the page explains that off Arch `ollama-cuda` adds no
package at all.

## A regeneration on this branch silently reverted this entry's own fixes

Recorded because the mechanism will catch the next person. `charly docs generate` reads the
`plugins/<plugin>/skills` PROJECTION, not the candy sources — `collectSkills`,
`candy/plugin-docs/gen_skills.go:85`. So a docs regeneration is only as correct as the `plugins`
checkout standing next to it.

Commit `c3eda4f3` ran `task docs:sync` moments after `plugins` had been reset to its pinned
gitlink for superproject hygiene. The generator therefore read the UNFIXED projection and emitted
`main`'s version of the page, reverting both of this entry's fixes — and the commit went in
describing changes its diff no longer contained. This PR's validator caught it by blob comparison:
`ollama.md` at `c3eda4f3` was byte-identical to `origin/main`.

The tell was in the diffstat and went unread: a change that ADDS a clarifying paragraph reported
5 insertions against 12 deletions. A net removal from an additive edit is a contradiction, and it
was visible before the commit.

Two operations must not be interleaved: parking submodule gitlinks at their pins, and regenerating
a projection that reads through one of them. The regeneration here was re-run with `plugins` on
its feat branch, and the result verified by asserting the page's CONTENT rather than its diffstat.
