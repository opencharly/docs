# 2026.299.0734 — fix(build): pin the node version to 22.23.4 — the floor the lockfile declares

## Summary

**Head `8817842593640d38f9e307e98c5fabe910503c6e` — 1 file changed, 1 insertion(+), 1 deletion(-).**

The lockfile this repo now ships declares a **node floor of `>=22.23.4`**, and the repo declared its node as the floating major `22` — which the CI resolved to **v22.23.3**, one patch below the floor. The deploy job was therefore installing the site's dependencies on a node they declare **unsupported**, and npm said so twice, in the install log, while still exiting 0.

This change pins the exact version the tree's dependencies require, so the install is clean and the declared toolchain and the declared requirement are the same fact.

| file | what it carries |
|---|---|
| `.node-version` | `22` → `22.23.4` — the exact node the lockfile's `engines` floors require |

**Why this is a defect and not a nicety.** A floating major cannot guarantee a floor: the floor was **published ahead of the alias's resolution**. `v22.23.4` was released on **2026-10-20**; the merged deploy run of opencharly/docs#187 executed on **2026-10-26** and `actions/setup-node@v7` still resolved `22` to `v22.23.3` — six days later — because it resolves through **its own version manifest**, not through the release feed. The requirement was met by luck, and the luck ran out on the day the floor was published.

**Why the exact version, and not a newer major.** The floor is `>=22.23.4`; `v22.23.4` is the newest `22.x` and satisfies it exactly. The repo stays on the node major it was already on — the change is the declared version, not the node line.

**Why there is still exactly one place that declares the node.** `.node-version` is where this repo has always declared it, and the deploy workflow reads it with `node-version-file: .node-version`. `package.json` gains **no** `engines` field: that would be a second source for the same fact, and the two would drift — the defect this issue is about, in a different file.
