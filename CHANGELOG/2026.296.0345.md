# 2026.296.0345 — docs(corpus): bump the vendored corpus pin to the corpus's merged main, and report the pin's currency

## Summary

Head `df52681cea24324117543b04ad794c5abe5dae3b`.

The site's recipe pages are a **projection** of the vendored `marketplace` corpus, and
the corpus pin this repo recorded was **14 commits behind** the corpus's merged main —
so every published `recipes/**` page was a projection of a corpus the org had already
replaced. This PR moves the pin to the corpus's merged main, regenerates the generated
half with the generation workflow's **own** inputs, and adds the **control** that stops
the next drift: the workflow now **reports** whether the pinned corpus is behind the
corpus's merged main.

**The regeneration is the workflow's own, with the workflow's own inputs** — the pinned
`charly` CI-time commit `bafd8dbc3110904872831998fb4caa701cc2990c`, the pinned umbrella
narrative commit `e631aacf32df4e26a66f2cb6a75fc9e85e212399`, the pinned `plugin-docs`
tag `v2026.289.0814`, and the new corpus checkout. The generated pages are never
hand-edited; they are the generator's own output, and the repo's own drift gate is the
definition of what a docs PR carries.

**The control answers the question the drift gate cannot.** The drift gate asks *"does
the committed content match what the PINNED inputs generate?"* — and the pinned corpus
generates its own old pages perfectly, so a stale corpus is invisible to it. The new
step asks the second question — *"is the pinned corpus itself current?"* — and answers
it. It is **reported, never failed**: a corpus that is behind is an advance available
NOW, the same shape the pin contract calls `behind`, and the remedy is a regeneration
PR that bumps the pin. A gate that failed here would be red on every push until
somebody ran that PR.

The same script, run against the **pre-change** tree's recorded pin, names the gap this
PR closes; run against this tree, it names the pin as current. Both runs are pasted
below.
