**The finding**, in the validator's words:

**The defect behind it, read in full.** Each harness asserted the mutation's anchor in **two** places: once in `emit()` and once again in `main()`, which then wrote the mutant itself. So the same rule was carried twice in one file, the copy in `main()` was the only one the workflow ever ran, and the `--emit` path — the one a diagnostic caller reaches — had no coverage and could drift away from the copy that gates. The two copies of a load-bearing rule, one of them unexercised, is exactly the shape R2 forbids.

**The fix is not to delete the utility. It is to make it the writer.** `main()` no longer asserts the anchor and no longer writes the mutant; it shells out to this harness's own `--emit` mode to write each mutant. Three properties follow, and each is a claim the evidence below carries:

| property | how it is obtained |
|---|---|
| the mode is covered **by construction** | the harness runs the very path a diagnostic caller runs — there is no second implementation of the mutation to keep in step |
| the anchor assertion lives in **exactly one** place | `emit()` is the only place the anchor is counted, and `main()` no longer counts it |
| the mutant the harness tests **is** the mutant `--emit` produces | the harness does not write a mutant at all; it asks `--emit` for one |

**Both harnesses move together** — the step-deadline harness this repo already had, and the advisory harness #191 added. Fixing only the new one would have left the repo with two harnesses of the same mechanism in two different shapes, which is the duplication R2 forbids. So both change, and the change is the same in each.

**The gate's outcome is unchanged.** All five mutants in each harness still turn the self-test red, and each still turns it red on the case that covers the mechanism it removes. This change moves *where* the mutant is written; it does not weaken what the harness proves.

### The one round-2 fix

This PR's own validator review of the first head returned `PASS` with **two non-blocking observations**. One is fixed here; one is rebutted on the PR thread with the evidence.

**Fixed — the two failure messages read alike.** A harness has two ways to fail before it mutates anything: the named mutant does not exist, or the mutant's anchor has moved. The first printed `FAIL: no mutant named 'x'`; the second printed `the anchor for … — the mutation cannot be applied …` with **no marker at all**. The exit code is the real signal — nothing in CI greps for the prefix — but two failure paths in one tool should read alike, and a reader scanning a CI log should not have to know which of the two messages carries a marker.

The fix is the prefix, **in BOTH harnesses** — the advisory one this PR rewrites and the step-deadline one it rewrites beside it. Fixing only the advisory one would have left the two siblings of the same mechanism reading differently, which is the duplication R2 forbids and the cutover rule (HC) names: *every sibling with the same mechanism moves together*.

Both harnesses now carry the marker on **both** failure paths, and the marker is asserted by a test that can fail — the harness itself, whose every mutant must turn the self-test red. **Nothing asserts on these messages; they are read by a human.** The gate's *outcome* is unchanged: five mutants per harness, every one still turning the self-test red on the case that covers the mechanism it removes.

**Correction (opencharly/docs#193).** The clause *"the marker is asserted by a test that can fail"* above is **false**, and the sentence right after it says so. Nothing asserts on the `FAIL:` marker: the mutation harness asserts that a mutant turns the **self-test** red — on the case that covers the mechanism it removes — and no CI step greps for the prefix, so the marker is a **human-facing** convention that makes the two failure paths of one tool read alike in a log. The **code** is unaffected by this note, and the change's central property is unchanged and still proven: every mutant in each harness turns the self-test red, five per harness, ten in total. This correction is appended rather than written over the sentence above, so the two can be read beside each other; the merged PR body carries the same text and is left standing for the same reason.

**Rebutted — the missing `timeout=`.** The validator notes that the harness's `subprocess.run` calls carry no `timeout=`, and calls it harmless. It is, and adding one would be a **regression in the failure mode**:

- the step already carries a deadline, and this repo's own gate asserts that every step does (5 min for the step-deadline harness, 10 min for the advisory one), so the set of child processes is bounded;
- the advisory harness's children make **live** network calls to the npm advisory database, and npm's own default fetch timeout is **300000 ms** — so any per-call timeout tighter than that would turn *"the registry is slow"* into a **red harness**;
- a red harness says *"the self-test can no longer fail"*, which is exactly the false signal this harness exists to avoid. A timeout would trade a visible timeout for a misleading verdict.

The full reasoning is on the PR thread.
