## What was still published

`keep_images` changed meaning in `candy/plugin-clean/retention.go`: it used to rank **tag rows**
and now budgets **two ordinals** — the newest N *distinct images* per `ai.opencharly.box` group,
and at most N tags of each. The producing repo's candy sources were corrected and the `plugins`
projection regenerated, but these two pages were never regenerated, so the **falsified** claim
stayed live on the public site:

- `recipes/build/build.md:244` — *"keeping the newest N builds per"*
- `recipes/build/build.md:256` — *"keep_images: 3 # newest CalVer tags to keep per image"*
- `recipes/core/clean.md:36` — *"keep_images: 3 # newest CalVer tags to keep per image"*

## How it was nearly missed, which is the transferable part

The check that cleared this repo searched for the **NEW** prose (`distinct image` → 0 hits) and
concluded *"docs is behind rather than orphaned-ahead, which is the safe direction."* **"Behind"
means the falsified claim is still published.** That is not the safe direction; it is the defect
still shipping.

> To check whether a correction propagated, searching for the **NEW** text tells you whether it
> ARRIVED. Searching for the **OLD** text tells you whether the false claim is still LIVE. Only
> the second question is about harm.

A search for the new text can only return a reassuring answer: absence reads as "not yet synced"
when it may equally mean "the wrong thing is still being served." The old-text search has no such
ambiguity — a hit is a live defect, by construction.

## Scope: exactly the two pages whose sources changed

`charly docs generate` also rewrites three `recipes/vm/*` pages. **They are excluded because
another leg owns them**, not because of anything about their diff: the `distro:` / cloud-init
projections are the subject of a live sibling PR, and a page with an owner should be regenerated
by that owner in one coherent change rather than picked up in passing by a change about something
else.

**An earlier revision of this entry gave a different and WRONG reason** — that the three diffs were
*"deletions of coherent prose, the signature of a stale-source revert."* Re-derived against the
pinned `plugins`, they are **30 insertions / 32 deletions**: a roughly balanced rewrite that ADDS
content present only at that pin — the pacman-family guests (`archarm`/`manjaro`/`endeavouros`/
`cachyos`) and the D15 host-key race. **This branch is AHEAD on those pages, not behind.**

The mistake is worth recording because it is the same one this entry exists to warn about, made
one paragraph away from the warning. The deletion heuristic was applied by running
`git diff | grep '^-' | head`, reading the removed lines, and concluding "deletions." **That
command can only show deletions.** It cannot report that more was added, so it can only ever
confirm the hypothesis it is used to test — the identical failure mode as searching for the NEW
text to decide whether an OLD claim is still live. Both are checks whose result is determined by
the question's polarity rather than by the tree.

A heuristic recorded as a finding in permanent history misleads every later reader, so the reason
is corrected here rather than quietly dropped. **The right instrument was `--numstat` on both
sides, and the right reason was ownership all along.**

## Why this leg had to be regenerated twice

`charly docs generate` reads the **plugins** tree, not the candy sources:
`candy/plugin-docs/gen_skills.go:81` resolves `skillsDir` as `<root>/plugins/<plugin>/skills`.
So a recipe page is a projection **of a projection**:

    candy/<name>/charly.yml  ->  plugins/<p>/skills/<s>/SKILL.md  ->  docs recipes/<p>/<s>.md

The first cut of this leg was generated before the `plugins` projection had been regenerated for a
later candy-source fix, so it published prose one step behind its own correction — the two pages
carried the `keep_images` fix but not the bounded tag cap that followed it.

**The order inside the chain is fixed, not a preference.** `docs` can never be current unless
`plugins` is regenerated first, because `docs` reads what `plugins` emits. The two producer legs
are not siblings; they are a chain, and a docs regeneration is only as fresh as the plugins tree
on disk when it ran.

**The check that finds this is not a reading.** A residue check proves nothing was ADDED; it
cannot prove nothing was OMITTED, because an absent sentence has no line to read. The only test
that catches a stale regeneration is to regenerate from the source head and require byte-identity.

## What the corrected prose says

`keep_images: N` keeps the newest N distinct images per box **and at most N tags of each**, where
a *distinct image* is a distinct image ID. It also now states **which verb reclaims what**: the
post-build pass cannot remove an image's last tag, so it never reclaims a distinct image — only
surplus tags of images wearing several. The distinct-image budget is enforced by `charly clean`,
and a project that only ever builds accumulates distinct images past `keep_images` with no
surface reporting it.
