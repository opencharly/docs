# 2026.299.0759 — fix(deps): clear the dev-tree undici advisories, and make the audit a gate

## Summary

**Head `2ae14526e95f8afdad9a11ac5d344c9dfc4b8835` — 6 files changed, 584 insertions(+), 3 deletions(-).**

This change does the two things opencharly/docs#163 asks for, and nothing else: **it clears the dev-tree `undici` advisories** that ride `wrangler` → `miniflare` → `undici`, and **it makes the dependency audit a gate** that fails the build on a finding in either tree.

|---|---|

| `package-lock.json` | the resolved consequence: `miniflare`'s nested `undici` moves `7.29.1` → `7.30.1`, three lines |
| `.github/scripts/check_dependency_advisories.py` | the gate: audits the tree the committed lockfile resolves, labels every finding `production` or `dev`, and **fails on a finding in either tree** |

**The override is version-qualified, and that is the correction.** The obvious shape — `{"miniflare": {"undici": "7.30.1"}}` — **breaks this repo's own CI**. The CI's node is `.node-version` (`22.23.4`), which carries **npm 10.9.9**, and npm 10 does not apply an override keyed on a *transitive* package: it ignores the nested entry, leaves the tree at `undici 7.29.1`, and its `npm ci` then **refuses the lockfile** that npm 11 wrote:

```
$ npm ci --no-audit --no-fund
npm error code EUSAGE
npm error
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error
npm error Invalid: lock file's undici@7.30.1 does not satisfy undici@7.29.1
```

`{"undici@7.29.1": "7.30.1"}` is honoured by **both** npm versions, and it is *more* precise than the nested form: it names the **vulnerable version**, so it does not pin a parent's exact beta release and it survives a `miniflare` bump. The four override shapes, each measured against both npm versions:

| override shape | npm 10.9.9 (CI) | npm 11.20.0 |
|---|---|---|
| `{"undici": "7.30.1"}` (top level) | honoured | honoured — but it also drags `astro`'s `unifont` from `undici 8.12.2` down to `7.30.1`, a **major downgrade of the production tree's HTTP client** |
| `{"miniflare": {"undici": "7.30.1"}}` | **ignored**, and `npm ci` fails | honoured |
| `{"wrangler": {"miniflare": {"undici": "7.30.1"}}}` | **ignored** | honoured |
| **`{"undici@7.29.1": "7.30.1"}`** | **honoured** | **honoured** — and it leaves the production tree's `undici 8.12.2` untouched |

**The `wrangler` advance the issue lists as the alternative does not exist.** Measured against the registry, not assumed: `wrangler@4.152.0` (the newest) depends on `miniflare 5.20261019.2-beta`, and that `miniflare` depends on `undici 7.29.1` — the same vulnerable version, inside the advisory's range `7.0.0 - 7.30.0`. There is no release of `wrangler` that carries a fixed `undici`, so the override is the only mechanism that clears this, and the issue's own ordering (override first) is the right one.

**The gate fails on a dev-tree finding too, not only a production one.** opencharly/docs#163 asks for "a gate that fails on a PRODUCTION-tree finding", and it names the reason the dev tree matters: *the deploy path is privileged* — `wrangler` holds the Cloudflare Pages token and parses responses from a remote service. A gate that only watched the production tree would have watched the tree that was already clean and missed the one that was not.

**The gate reads the lockfile, not an install.** It runs `npm audit --json` and `npm audit --omit=dev --json` against the committed lockfile, so it does not depend on an install having run and it cannot drift from the tree `npm ci` installs. **A tree npm cannot audit is an error, never a pass**: npm reports `ENOLOCK` in the same JSON channel it reports findings in, so a report without a `vulnerabilities` map fails the check loudly instead of reading as an empty audit.

**The gate follows this repo's existing gate shape rather than inventing a second one.** `.github/scripts/check_step_timeouts.py` already carries the pattern this change follows: the checker, a `--self-test` mode that drives it against real fixtures, a separate mutation harness that proves the self-test can fail, and workflow steps that run all three. The self-test drives the **real** `npm audit` against **real** fixtures — a production finding, a dev finding, a clean tree, and a tree npm cannot audit — against the **real** npm advisory database. The vulnerable fixture is pinned to `postcss-selector-parser@6.1.4`, a **published** advisory (`GHSA-rj75-hqrm-r3gf`) with a fixed upper bound, so the fixture does not drift with a transitive bump and is not a hand-written advisory the checker trusts because the checker was told about it.

Measured: (a) npm 10.9.9 does not apply an override keyed on a transitive package, so the nested form is ignored and `npm ci` then refuses the lockfile npm 11 wrote — `Invalid: lock file's undici@7.30.1 does not satisfy undici@7.29.1`; (b) npm 10.9.9's `npm install --package-lock-only` **strips** the `libc` fields npm 11 wrote — 26 changed lines out of 102, against 3 out of 3 when the same lockfile is generated with npm 11. The root fix is a declared `packageManager` plus a corepack-pinned npm in CI, so one npm resolves the lockfile. It is a change in this repo, but it is separable from this one — this change works under **both** npm versions, which is exactly why the override was written the way it was — so it is filed rather than folded in.
