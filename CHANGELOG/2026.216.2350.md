# 2026.216.2350 — every abbreviation resolves

`IR`, `CUE`, `OCI`, `MCP`, `RPC`, `CalVer`, `ADE`, `RDD`, `SDD`, `SDK` and the probe protocols
(`CDP`, `VNC`, `ADB`) were used across the site with no consistent point of expansion. An
abbreviation nobody expands is noise to a reader meeting it cold, and when it sits in the sentence
carrying a page's main claim, that claim becomes unreadable — which is not meaningfully different
from never having made it.

[The abbreviations](/concepts/00-vocabulary/#the-abbreviations) is now a table on the glossary page,
expanding each one and saying what it means *here* rather than in general.

Two earn the detour. **IR** is the compiler term for the neutral form in the middle — the shared
install plan produced once from a candy list and consumed by the container, VM, cluster, host and
Android backends alike. That is exactly why `pod:` → `vm:` is a keyword change, so a reader who
skipped the abbreviation skipped the mechanism behind the site's headline claim. **CUE** is a schema
language (*Configure, Unify, Execute*) rather than an initialism anyone expands in speech, and the
table says so instead of pretending otherwise.

First uses elsewhere are expanded inline or linked to that table. The home page gets its share
through the generator rather than by hand — the superproject's `README.md` expands CLI, OCI, MCP,
API and CalVer on first use, and `index.md` is regenerated from it.

## Polymorphism and nesting, explained precisely

Two ideas a newcomer trips over, and the docs were making both harder than they are.

**Polymorphism was framed as a choice between three types.** "One candy, three roles", under a
column headed *What it is*, reads as a type switch: pick layer, box or plugin. The schema does not
work that way, and the tree disproves it — **all 86** plugin candies in the charly repository also
carry `package:` and `plan:`. A plugin candy is a layer that additionally registers a verb.

The framing is now additive: you never declare what kind of thing you are writing, you add fields,
and each field *adds a capability*. **A candy is a set of capabilities, and these words describe
which ones it has.** That also dissolves an apparent contradiction — `charly box build` and
`charly box list candies` acting on the same file — which the old framing made look like a bug.

**Nesting is a different idea, and conflating the two is the other half of the confusion.**
Capabilities compose a *candy* at authoring time; nesting places a *deploy* at run time. A candy is
never inside another candy; a deploy can be inside another deploy. There is no `nested:` field —
nesting is position in the file, shown with a real `check-group` excerpt where a `local:` deploy
indented under a `vm:` node lands inside the guest and carries no `host:` field because it inherits
the parent's venue.

The consequence matters more than the mechanism: a top-level `local:` deploy installs onto the
machine charly runs on; the same four lines nested under a disposable `vm:` install into a throwaway
guest. Identical authoring shape, different position — and that position is the difference between
editing your workstation and editing something built to be destroyed.

**Nesting is not membership**, stated outright because the file shapes resemble each other: a deploy
indented *under* another runs **inside** it; a sibling member runs **beside** it, reachable at
`${HOST:<member>}`. Children go in; siblings go next to.

## The polymorphism goes further than "three roles"

The additive framing above was still short of the real architecture, and the missing half is the
more striking one: **every keyword on this site is registered by a plugin candy.**

`charly` is not a program with built-in support for containers, VMs and Kubernetes that also accepts
plugins. Its core is *kind-blind* — it loads plugins, routes a word to whichever one claims it, and
carries generic data between them. It does not know what `pod:` means.

The catalog registers **128 words across 80 plugin candies**: 7 deploy substrates, 16 kinds, 41
check verbs, 46 commands, 13 install steps, 5 builders. Every figure re-derived from the tree at
write time.

The second row is the one to sit with: **`candy:` itself is a plugin-provided kind**, registered by
`candy/plugin-candy-kind`. The keyword the vocabulary page is *about* is not privileged — it is a
word some candy claimed.

So there is no fixed list of substrates, no fixed list of check verbs, and no built-in set to
petition for additions to. A plugin is compiled in or loaded from a project's own `candy/` directory
— including a project that is not charly's, referenced by git URL. You extend `charly` by writing
candies, as many as you like, and a substrate you invent is the same kind of thing as `pod:`.

That is the actual reason the core stays small while the catalog grows, and the docs had been
stating the conclusion without the mechanism: extending the tool and using the tool are the same
activity.

## The architecture, not just the surface it presents

The site described what charly accepts and what it produces and stopped there. A reader could learn
the vocabulary, the roles and the stages without ever learning *how* any of it works — leaving every
interesting claim ("swap the substrate, not the recipe", "the core stays small") as something to take
on faith.

Six steps now, each verified against the tree: one resolved project → a core that does not know what
anything means → plugins reached identically wherever they live → build and deploy diverging then
rejoining on the shared install plan → an artifact carrying its own description in `ai.opencharly.*`
labels → a CUE schema upstream of the types, the validation and these pages.

Two facts do the most work. **`deploy:pod`, `deploy:vm` and `deploy:local` are out-of-process** —
the substrates everyone assumes are built in are not even in the binary; 53 of 81 plugin candies are
compiled in and 28 are not. And the **install plan** is the thing "swap the substrate" was always
describing: build renders a Containerfile, deploy compiles the same candy list into one intermediate
representation, and each backend realises it its own way.

Then what the shape makes possible, framed as consequences rather than features: invent a substrate,
compose across organisations by git URL, run charly inside charly, hand it to an agent, prove it
disposably.

**Counts corrected, and the error is worth recording.** The figures published earlier in this entry —
"128 words across 80 plugin candies" — were wrong by one in both places. The extraction pattern was
`[a-z0-9-]+`, which silently excluded `verb:unix_group`. The true figures are **129 words across 81
candies**, and 42 verbs rather than 41. A regex that under-matches yields a plausible number rather
than an obvious failure, which is why every figure here is re-derived at write time.
