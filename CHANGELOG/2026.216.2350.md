# 2026.216.2350 — every abbreviation resolves

`IR`, `CUE`, `OCI`, `MCP`, `RPC`, `CalVer`, `ADE`, `RDD`, `SDD`, `SDK` and the probe protocols
(`CDP`, `VNC`, `ADB`) were used across the site with no consistent point of expansion. An
abbreviation nobody expands is noise to a reader meeting it cold, and when it sits in the sentence
carrying a page's main claim, that claim becomes unreadable — which is not meaningfully different
from never having made it.

[The abbreviations](/concepts/00-vocabulary/#the-abbreviations) is now a table on the glossary page,
expanding each one and saying what it means *here* rather than in general.

Two earn the detour. **IR** is the compiler term for the neutral form in the middle — the shared
install plan produced once from a candy list and consumed by the container, VM, cluster, host and
Android backends alike. That is exactly why `pod:` → `vm:` is a keyword change, so a reader who
skipped the abbreviation skipped the mechanism behind the site's headline claim. **CUE** is a schema
language (*Configure, Unify, Execute*) rather than an initialism anyone expands in speech, and the
table says so instead of pretending otherwise.

First uses elsewhere are expanded inline or linked to that table. The home page gets its share
through the generator rather than by hand — the superproject's `README.md` expands CLI, OCI, MCP,
API and CalVer on first use, and `index.md` is regenerated from it.

## Polymorphism and nesting, explained precisely

Two ideas a newcomer trips over, and the docs were making both harder than they are.

**Polymorphism was framed as a choice between three types.** "One candy, three roles", under a
column headed *What it is*, reads as a type switch: pick layer, box or plugin. The schema does not
work that way, and the tree disproves it — **all 86** plugin candies in the charly repository also
carry `package:` and `plan:`. A plugin candy is a layer that additionally registers a verb.

The framing is now additive: you never declare what kind of thing you are writing, you add fields,
and each field *adds a capability*. **A candy is a set of capabilities, and these words describe
which ones it has.** That also dissolves an apparent contradiction — `charly box build` and
`charly box list candies` acting on the same file — which the old framing made look like a bug.

**Nesting is a different idea, and conflating the two is the other half of the confusion.**
Capabilities compose a *candy* at authoring time; nesting places a *deploy* at run time. A candy is
never inside another candy; a deploy can be inside another deploy. There is no `nested:` field —
nesting is position in the file, shown with a real `check-group` excerpt where a `local:` deploy
indented under a `vm:` node lands inside the guest and carries no `host:` field because it inherits
the parent's venue.

The consequence matters more than the mechanism: a top-level `local:` deploy installs onto the
machine charly runs on; the same four lines nested under a disposable `vm:` install into a throwaway
guest. Identical authoring shape, different position — and that position is the difference between
editing your workstation and editing something built to be destroyed.

**Nesting is not membership**, stated outright because the file shapes resemble each other: a deploy
indented *under* another runs **inside** it; a sibling member runs **beside** it, reachable at
`${HOST:<member>}`. Children go in; siblings go next to.
