**The site stops trailing its producers, and nothing trails it silently any more.** Two things land here, and they are the two halves of one question: *is each pinned input the site is generated from current?*

**1 — the report.** The site is generated from THREE pinned inputs: the guidance corpus (this repo's `marketplace` gitlink), the `charly` commit the deploy clones, and the umbrella commit the deploy clones. Every one of them is advanced by a MANUAL act after its producer lands, so the site trails its producers by however long nobody ran the regeneration PR — and the drift gate CANNOT see it, because the PINNED sources regenerate their own (old) pages perfectly. The drift gate answers "does the committed content match what the pinned inputs generate?" (yes, always); it never answers "is each pinned input itself current?".

`.github/scripts/check_pin_currency.sh` answers that second question for **all three** pins, and `.github/scripts/check_corpus_currency.sh` — which watched the corpus alone — is deleted in the same cutover (R5). The report speaks the pin contract's own vocabulary and its own states:

- `cur` — at the producer's merged main. Obligates nothing.
- `behind` — N commits behind the producer's merged main. An advance available NOW.
- `not-on-the-served-line` — the pin is off the producer's main line. A squash-advance, whose one remedy is the same as `behind`'s. NOT a divergence, and the report never calls it one.
- `undecidable` — the producer's history is shallow and could not be deepened, so ancestry cannot be judged.
- `unreadable` — the pin, or the producer's merged main, could not be read.

**The answer is REPORTED, never failed.** A pin that is behind is an advance available now — the same shape the pin contract calls `behind`: a reportable state, not a broken edge. A gate that FAILED on it would be red on every push until somebody ran the regeneration PR, and the remedy is that PR, not a gate. The report exits 0 in every state, and its fixtures assert that.

**The judgment must be DECIDABLE before it is reported.** `merge-base --is-ancestor` answers "not an ancestor" for a commit the clone does not have — indistinguishable from a real squash-advance. The corpus checkout in CI IS a depth-1 clone (actions/checkout runs `git submodule update --init --force --depth=<fetch-depth>` with its default `fetch-depth: 1`). A depth-1 history therefore cannot judge ancestry at all, and reporting from it would state a FALSE state — a divergence for a pin that is merely behind, with a wrong commit count. So a shallow history is DEEPENED first, and when the deepening cannot be done the report says `undecidable` and never guesses: **a false state is worse than no report.**

**The pins are recorded ONCE.** The two CI-time pins live in the workflow's own `env:` block, which the deploy's clone step consumes and this report reads — one record, one occurrence of each SHA in the whole repository, so a SHA can no longer be written in one place and forgotten in the other. The corpus pin is the committed gitlink, and it is read from the commit's TREE rather than from the checkout's HEAD: the checkout is a convenience, the tree entry is the pin.
