# 2026.215.1135 — Deploy to Cloudflare Pages from GitHub Actions

The site is published at [opencharly.ai](https://opencharly.ai) by a workflow in this repo rather
than by Cloudflare's own Git integration.

## Why not Cloudflare's Git integration

Connecting a Pages project to a GitHub **organization** requires an OAuth handshake that
Cloudflare must initiate, and there is no API for it: `POST /accounts/{id}/pages/connections`
returns `405 method_not_allowed` — the endpoint is GET-only by design. GitHub is the same on its
side: `POST /orgs/{org}/installations` is a 404, because installing an App is a consent grant, not
a resource you can create. Installing the Cloudflare App on the org (done) satisfies GitHub's half
and leaves Cloudflare's half unwritten, which is exactly the state that produced error 8000011 on
every project-creation attempt.

No token permission changes this; a 405 is "this operation does not exist", not "you may not".

So the project is Direct Upload, and this workflow does the build and the deploy with an API
token — reaching the same end state (production on `main`, preview deployments on pull requests)
without a manual step.

## The trade-off, stated

The Cloudflare API token lives in this repository's Actions secrets. It is scoped to Cloudflare
Pages edit plus DNS edit on the `opencharly.ai` zone, and nothing else. Moving to Cloudflare-native
Git builds later means recreating the project — Direct Upload cannot be converted in place.

## What the workflow gates

`npm ci` rather than `npm install`, deliberately: it installs strictly from the committed lockfile
and fails if that lockfile disagrees with `package.json`. A lockfile missing one of rolldown's
optional platform bindings shipped here once and would have broken the deploy at install time, so
this is a real gate rather than a formality. The build is then asserted to have produced
`dist/index.html` before anything is uploaded.

The site's link-integrity gate is not run here — it lives in `charly docs generate` in the charly
superproject, which this repo does not have. What CI proves is narrower and worth stating exactly:
the committed content builds cleanly from a clean install on a clean machine.

**wrangler is a pinned devDependency**, which is load-bearing rather than tidiness. Without it,
`wrangler-action` cannot find the binary and falls back to `npm i wrangler@4` inside the
checkout — an unpinned install *outside* the lockfile, performed in the job that holds the
Cloudflare token, which also mutates tracked package files and therefore stamps every deployment
`commit_dirty: true`. Arguing for `npm ci` and then installing a floating dependency two steps
later gives the whole rationale away. Pinning it fixes the supply-chain gap, the dirty-tree
warning, and the deployment metadata together; `--commit-dirty=true` would only have silenced
the symptom.

## Site fixes

- **Duplicate home-page title.** Starlight appends the site title to every page title, so a home
  page named `OpenCharly` on a site named `OpenCharly` rendered the browser tab as
  `OpenCharly | OpenCharly`. The home page now overrides its own `<title>`; every other page
  keeps the useful `Page | OpenCharly` form (`Install | OpenCharly`).
- **No table of contents on the landing page.** Starlight's `getToC` hard-codes the TOC to
  `false` when `template: splash`, before it ever consults the `tableOfContents` frontmatter —
  and `hasSidebar` is likewise `template !== 'splash'`, so a splash page can have neither
  sidebar. Setting `tableOfContents: true` is silently ignored. The landing page is now
  `template: doc`, which renders the hero exactly the same way (the hero renders on any template
  carrying a `hero:` block) while gaining both the navigation sidebar and the on-page TOC.
